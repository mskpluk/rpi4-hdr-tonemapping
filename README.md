# HDR10 to SDR tone mapping in the Raspberry Pi 4 display hardware

Hardware PQ (HDR10) to SDR tone mapping for LibreELEC 13 / Kodi 22 on the
Raspberry Pi 4. The video stays on a DRM plane and is decoded and displayed
zero-copy. The BT.2390 curve is applied by the gamma block of the display
controller (HVS), so tone mapping costs no GPU time. Kodi composites menus,
OSD and subtitles through the inverse of the curve, so they still look like
SDR.

**Development build.** LibreELEC 13 has not been released yet; the latest
release is 12.2.1. This is built from LibreELEC master of 6 November 2026,
the same code as the LibreELEC 13 nightlies, with Kodi 22 from the Piers
branch, after 22.0 RC1 and before the final release. Expect the bugs of a
development version.

Tested on a Raspberry Pi 4 Model B with a Samsung S85F, at 1080p and 4K. All
15 HDR test files (HDR10, HDR10+, Dolby Vision with an HDR10 base layer and
Dolby Vision profile 5, 4K at 23.976 to 59.94 fps) play at full frame rate
with the curve on.

## The problem

The Pi 4 decodes 4K HEVC in hardware, and Kodi shows the frames directly on a
DRM plane (DRM PRIME). That path has no tone mapping:

- **Kodi's tone mapping is shader-only.** Reinhard, ACES and Hable run in the
  GL/GLES video shaders. They need every frame converted and drawn by the GPU,
  which the Pi 4 cannot do for 4K: a 4K remux played at about 12 fps through
  the EGL path.
- **The display controller has no colour management in KMS.** On BCM2711 the
  CRTCs expose no `GAMMA_LUT`, `DEGAMMA_LUT` or `CTM`, so there is no standard
  way to apply a curve after composition.

On a TV without HDR, or with HDR output turned off in Kodi, PQ video was sent
as if it were SDR, looking flat and washed out.

## How it works

The HVS (Hardware Video Scaler) composites the planes of each display channel.
On BCM2711, every channel ends in a gamma block: a piecewise linear function
(PWL) with 16 points for each of R, G, B and alpha. The firmware loads a
curve of about x^(1/2.2) into it and leaves it disabled. The 16 points are
programmable. Each point is two words: X (31:20) | C (U12.4) and a gradient
(U4.8). The output is `C + (x - X) * gradient`.

### The curve

The default curve is generated by [`tools/pwl_gen.py`](tools/pwl_gen.py):

1. **[ITU-R BT.2390](https://www.itu.int/pub/R-REP-BT.2390) EETF in the PQ
   domain.** Source peak 4000 cd/m², target peak 203 cd/m². 203 cd/m² is the
   HDR reference white of BT.2408, so it becomes SDR 100 % white. Below the
   knee (`KS = 1.5 * maxLum - 0.5` in normalised PQ, here about 40 cd/m²)
   the signal passes unchanged. Above it, the BT.2390 Hermite spline rolls
   highlights off into the target peak.
2. **Back to light, then BT.1886.** The result is decoded to cd/m², divided
   by 203 and encoded with a 2.4 power for the SDR display.
3. **16-point PWL fit.** Knots are placed greedily, bisecting on the maximum
   error. The maximum error is 7 of 4095 codes (0.2 %).

| Source (cd/m²) | PQ | Output | Displayed, % of SDR white |
|---:|---:|---:|---:|
| 0.1 | 0.062 | 0.043 | 0.1 |
| 1 | 0.150 | 0.111 | 0.5 |
| 10 | 0.300 | 0.286 | 5.0 |
| 100 | 0.508 | 0.697 | 42.1 |
| 203 | 0.581 | 0.825 | 63.0 |
| 1000 | 0.752 | 0.979 | 95.1 |
| 4000 | 0.903 | 0.999 | 99.7 |

203 cd/m² lands at 63 % rather than 100 % because the spline already
compresses everything above the 40 cd/m² knee. The curve reaches white only
at the 4000 cd/m² source peak.

### Colour

The plane's YCbCr to RGB matrix (CSC) is replaced while the curve is on:
BT.2020 limited range YCbCr to RGB, with an approximate BT.2020 to BT.709
gamut conversion folded in. Gamut conversion belongs in linear light, but
the HVS has no linear stage, so the matrix was fitted in the PQ domain against
the exact conversion, within the range of the CSC coefficients (-1 to just
under 3, as described in `vc4_regs.h`). The matrix ignores the plane's
`COLOR_ENCODING` property, because decoders do not always report the colour
space and Kodi then leaves it at BT.709.

The error was measured on 8 frames from 7 UHD Blu-ray films, 2.8 million
non-black pixels. Both sides went through the same curve, so only the gamut
handling differs:

| | Mean | 95th percentile | 99th percentile | Max |
|---|---:|---:|---:|---:|
| HVS matrix | 1.0 | 3.4 | 6.8 | 29.8 |
| No gamut conversion | 4.4 | 15.7 | 24.0 | 41.9 |

The error is CIE76 ΔE against the exact conversion in linear light. The
largest errors come from rare, very saturated pixels outside BT.709, which
the exact conversion clips.

### The GUI

The curve applies to everything on the channel, GUI included. The gamma block
sits after the planes are composited, and the planes themselves only have a
matrix, so there is no way to apply the curve to the video plane alone. The
curve reads every pixel as PQ. Without compensation, a 50 % grey in the menu
would be read as about 92 cd/m² and shown at 41 % of white instead of 19 %.
Black and white barely move, so a dark OSD with white text hides most of
this; mid greys and coloured subtitles show it. The curve is only on during
PQ playback, so menus outside playback are never affected.

Kodi 22 already composites the GUI into an FBO for HDR output. The output here
stays SDR, but the same mechanism is reused: the composite shader gets one
more mode, a 256-entry LUT with the inverse of the curve. Kodi reads the
curve from `hvs5_pq_pwl` and inverts it by bisection. After the hardware curve,
menus, OSD and text subtitles come out as they would in SDR, within 1.2
code values at 8 bits. PGS subtitles with a PQ palette are drawn like video
and are tone mapped with it.

## Hardware behaviour found on the way

None of this is in public documentation. All of it was found by testing on a
running Pi 4.

- **PWL write lock.** The PWL SRAM of a channel ignores writes once that
  channel has run since power-on. The firmware uses channel 1 at boot and the
  kernel normally gives HDMI0 channel 0. Channel 2 is unused, so the curve is
  loaded there at bind time and read back for verification, and HDMI0 is
  steered to channel 2. Because of the lock, the curve cannot be changed
  until the next reboot.
- **Gamma enable bit.** Setting `SCALER_DISPBKGND_GAMMA` on a running channel
  works. Clearing it on a running channel stalls the channel for good: flip
  timeouts, and a black screen until power-off. The bit is therefore only
  changed while the channel is being (re)initialised in a modeset.

## Changes

### Linux (raspberrypi/linux 6.18, `drivers/gpu/drm/vc4`)

Opt-in: nothing changes unless `vc4.hvs5_pq=1` is on the kernel command line.

| Parameter | Mode | Meaning |
|---|---|---|
| `hvs5_pq` | 0444, command line | Load the curve into channel 2 at boot. HDMI0 then takes channel 2. |
| `hvs5_pq_gamma` | 0644 | Apply the curve on HDMI0 from the next modeset. |
| `hvs5_pq_crtc` | 0444 | DRM object ID of the CRTC the curve applies to, 0 if none. |
| `hvs5_pq_pwl` | 0444 | The curve: 32 words, can be replaced on the command line. |
| `hvs5_pq_gamut` | 0644 | Use the BT.2020 to BT.709 plane CSC while the curve is on (default on). |
| `hvs5_pq_csc` | 0644 | The three CSC words for that matrix. |

- **Decision in the atomic check.** `vc4_crtc_state.pq_to_sdr` decides it.
  The value is carried through `duplicate_state`. When it changes on a
  commit that allows a modeset, a modeset is forced, because Kodi only marks
  the CRTC active and keeps the same mode.
- **Channel choice.** HDMI0 prefers channel 2 when the curve is loaded.
  Channels are only assigned when an output is enabled, so HDMI0 keeps
  channel 2 even while the curve is off.

### Kodi (Piers, GBM/GLES)

1. **[DRMPRIME] Map PQ to SDR with the Raspberry Pi 4 HVS curve.**
   `CWinSystemGbm::SetHwToneMapping()` writes `hvs5_pq_gamma` and forces a
   modeset. While the curve is on, the connector colorimetry is set to
   default (BT.709), because that is what the curve outputs.
2. **[DRMPRIME] Add the hardware BT.2390 tone mapping setting.** "BT.2390"
   is added to the video settings tone mapping methods. It is offered only
   when `hvs5_pq_crtc` matches the CRTC Kodi drives, and then it is the only
   method besides Off. Shader renderers treat a saved BT.2390 as Hable.
3. **[GBM] Clear HDR metadata when HDR display mode is turned off during
   playback.** See below.
4. **[GBM] Composite the GUI through the inverse Raspberry Pi 4 HVS curve.**
   If the GUI cannot be composited this way, the curve stays off.
5. **[guilib][GLES] Keep GUI translucency in HDR compositing.** See below.
6. **[GUI] Reload the skin when the screen aspect ratio changes.** See
   below.
7. **[GBM] Update the resolutions on display hotplug.** See below.
8. **UPnP: fix serving files after the path traversal fix.** Backport of
   [xbmc/xbmc#30351](https://github.com/xbmc/xbmc/pull/30351), unrelated to
   HDR.

### What was wrong in Kodi's HDR handling

These were found while testing the curve. Most of them affect every GBM
device, not just the Pi.

- **HDR metadata stuck after turning HDR off.** Turning off "Adjust display
  HDR mode" (Settings → Player → Videos) during playback left the TV in HDR
  mode. `CWinSystemGbm::SetHDR()` returned early when the setting was off and
  never cleared `HDR_OUTPUT_METADATA` or `Colorspace`. With the curve, the
  picture was tone mapped twice: once by the Pi, once by the TV. Now
  `SetHDR()` clears the metadata it set, and the renderer reconfigures when
  the setting changes. Kodi master has the same code.
- **The kernel cannot tell that the content is PQ.** Kodi sets
  `HDR_OUTPUT_METADATA` only for displays that support HDR. That is why the
  curve is switched by Kodi and not by the driver.
- **Translucent OSD drawn with squared alpha.** In HDR compositing the GUI
  FBO was blended with premultiplied alpha and composited again with its
  alpha. A 50 % OSD bar covered the video only 25 %. The FBO now keeps
  straight coverage, and the composite shader un-premultiplies.
- **Squashed GUI after a 4:3 start.** Kodi started at 1024x768 when the TV
  was asleep (see the next item). After switching to 1920x1080, the windows
  kept in memory stayed in the 4:3 skin coordinates, and the whole GUI was
  squashed into the top three quarters of the screen
  ([#25875](https://github.com/xbmc/xbmc/issues/25875)). The skin is now
  reloaded once the aspect ratio has settled for 500 ms, except during
  screen calibration; a change during video playback is picked up when
  playback stops. Submitted upstream as
  [xbmc/xbmc#30385](https://github.com/xbmc/xbmc/pull/30385).
- **No display hotplug on GBM.** A TV in standby can return an all-zero EDID.
  The Samsung S85F does, and Kodi then only gets the VESA fallback modes. When
  the TV wakes, the kernel reads the EDID and sends a hotplug uevent, but
  Kodi never probed the connector again. Kodi now watches the drm uevents and
  waits 2 s for the hotplugs to settle. If the modes changed, it updates the
  resolutions and applies the one from the settings again; the saved setting
  itself is never overwritten. Probes without an EDID are ignored, so a TV
  going to sleep keeps its modes. Video playback and modal dialogs delay the
  update until they end.

Known, not fixed: Kodi deadlocks when a resolution change, for example the
refresh rate switch at the start of playback, happens while a settings window
is open. `CGUIWindowSettingsCategory` saves the new resolution on
`GUI_MSG_WINDOW_RESIZE`, and the "keep this resolution?" dialog opens while
the settings lock is held. Inside that dialog, the switch to full screen
video closes the settings window, which waits for the same lock. This is in
upstream Kodi code.

## Comparison

**Kodi's Hable.** Kodi's own methods (Reinhard, ACES and Hable) could not be
used, for two reasons:

- **Renderer.** They exist only in the GL/GLES shader renderer, which cannot
  draw 4K fast enough on the Pi 4.
- **Fixed curve.** They scale the curve to each title, using a luminance value
  derived from its metadata (MaxCLL, MaxFALL and the mastering display peak).
  The HVS curve cannot be rewritten once the channel has run, so it has to be
  one curve for everything.

Kodi's shader path also has two calculation choices that change the
picture:

- **Gamut conversion on the PQ signal with mismatched exponents.** Before
  tone mapping, the shader treats the PQ signal as if it were a 2.4 gamma
  signal: `pow(rgb, 2.4)`, the BT.2020 to BT.709 matrix, then `pow(rgb,
  1/2.2)`. The result then goes into the PQ decoding as if it were still
  PQ. Because the two exponents differ, even greys come out darker: 100
  cd/m² is read as 74 cd/m², 203 as 155, 1000 as 838. Measured like the HVS
  matrix above, the colour error is ΔE 4.4 on average (95th percentile 7.0).
  With the same exponent both ways, the same shortcut would give 0.9.
- **Hable white point.** The shader multiplies the light by `2 / lumin`
  and scales Hable's white point to `lumin / 100`, where `lumin` comes from
  the metadata. So the curve reaches white at half of the metadata value.

With both effects included, and assuming a 2.4 display for all of them:

| Source (cd/m²) | Kodi Hable, 1000 cd/m² metadata | Kodi Hable, 4000 cd/m² metadata | This curve |
|---:|---:|---:|---:|
| 1 | 0.3 % | 0.2 % | 0.5 % |
| 10 | 3.9 % | 3.2 % | 5.0 % |
| 100 | 38.3 % | 30.7 % | 42.1 % |
| 203 | 62.3 % | 50.0 % | 63.0 % |
| 1000 | 100 % | 89.8 % | 95.1 % |

With 1000 cd/m² metadata, Kodi's Hable turns everything above about 600
cd/m² white. With 4000 cd/m² metadata, everything above about 2300 cd/m² is
white. This curve rolls off up to a fixed 4000 cd/m², so bright skies and
fire keep their detail. It is also slightly brighter in the mid tones,
because nothing darkens the signal before the curve.

**Better or worse than Kodi's Hable?** Better in most respects, worse in
one:

- **Highlights: better.** Kodi's Hable turns everything above its white
  point white. With 1000 cd/m² metadata that is everything above about
  600 cd/m². When the metadata is missing, Kodi assumes 400 cd/m², and then
  it is everything above about 260 cd/m², so whole skies clip. BT.2390 keeps
  gradation all the way to 4000 cd/m².
- **Shadows and mid tones: better.** Below its knee (about 40 cd/m²),
  BT.2390 leaves the picture as graded. Kodi's Hable has a toe that darkens
  the shadows, and it gets a darkened input from the exponent mismatch.
  With real metadata it is darker in the mid tones: 100 cd/m² gives 31–38 %
  instead of 42 %.
- **Colour: better.** The gamut error is ΔE 1.0 on average, against 4.4.
- **Predictability: better.** The curve is the one described in the ITU-R
  BT.2390 report, and mpv used it by default. It does not depend on
  metadata, which is often missing or wrong. Hable is a filmic curve from
  games rendered in linear light, not made for PQ video.
- **Adaptation: worse.** Hable follows each title's metadata, so a title
  graded to 1000 cd/m² uses the whole output range. This fixed curve keeps
  room for 4000 cd/m², so a 1000 cd/m² peak lands at 95 % white and such
  titles are a little less punchy in the highlights. There is no user
  parameter either; the curve can only be changed at boot.

Both apply the curve to each RGB channel, so neither keeps the hue of very
bright saturated colours.

Watching films on the same TV and switching between the two, this curve
with the gamut matrix gives a picture that looks more like a proper SDR
grade than Kodi's Hable. That is a subjective impression.

**mpv.** mpv offers the same BT.2390 EETF. It was the default tone mapping
function of `vo=gpu`, with a 203 cd/m² reference white. `vo=gpu-next`
(libplacebo) still offers it, but its automatic choice is `spline`
([mpv wiki](https://github.com/mpv-player/mpv/wiki/GPU-Next-vs-GPU)). mpv does
it in shaders, which allows things a fixed hardware curve cannot do:

- measuring the peak brightness of each scene or using HDR10+/Dolby Vision
  metadata instead of a fixed 4000 cd/m² source;
- tone mapping luminance or a perceptual colour space instead of each RGB
  channel separately (selectable with `tone-mapping-mode`);
- gamut mapping in linear light (`gamut-mapping-mode`).

The price is GPU time for every frame, which the Pi 4 does not have at 4K.

**The TV.** An HDR TV given the HDR signal does its own tone mapping and
should look better. This curve is for SDR TVs, or for HDR TVs where the HDR
mode is worse than the SDR one, for example a TV whose HDR mode only allows
some picture presets.

## Performance

Tested with 15 HDR files at 4K: six UHD Blu-ray remuxes of up to 80 Mb/s
(average, with lossless audio), web releases, and demo clips up to 59.94 fps
with a 76 Mb/s HEVC stream. With the curve on, every file kept its full frame
rate at the matching display refresh rate. The decoder delivered every frame,
the display flipped on every refresh, and the media clock ran at real time.
This was measured with ftrace (`v4l2_dqbuf` on the HEVC decoder and
`drm_vblank_event_delivered`) and the player time from JSON-RPC.

The curve runs in the display pipeline, so it adds no CPU or GPU work.

The Pi ran at stock clocks with `hdmi_enable_4kp60=1` in `config.txt`, which
4K at 50/60 Hz needs. That option raises the core, HEVC and V3D clocks from
500 to 550 MHz. With passive cooling, the Pi reached at most 73 °C and did not
throttle. 4K at 60 Hz also needs a TV input that accepts it; on Samsung that
is "Input Signal Plus".

## Limitations

- **BCM2711, HDMI0 only.** Pi 5 is not supported. Kodi checks
  `hvs5_pq_crtc` and hides the setting elsewhere.
- **Static curve.** It is fixed to 4000 to 203 cd/m², does not follow the
  metadata of each title, and cannot change until reboot (PWL write lock).
- **Per-channel curve.** The curve is applied to R, G and B separately, so
  very bright saturated colours shift towards white or yellow, for example
  orange fire.
- **Approximate gamut.** The gamut matrix is an approximation in the PQ
  domain.
- **Dolby Vision profile 5** is not PQ in the BT.2020 sense, so it is not
  tone mapped.
- **TXP writeback.** With the curve loaded, TXP writeback does not work while
  HDMI0 is on, as it needs channel 2. If TXP already holds channel 2 when
  HDMI0 is enabled, HDMI0 gets another channel without the curve, and Kodi
  does not detect that.
- **Kernel interface.** The switch is a module parameter written from user
  space, not a KMS property. KMS has no standard property for "show PQ
  content on an SDR display". The standard gamma property (`GAMMA_LUT`)
  promises a curve that can be replaced at any time, which this hardware
  cannot do once the channel has run. vc4 offers `GAMMA_LUT` only on the
  older HVS of the Pi 0–3. A driver-specific CRTC property would be the
  KMS-style alternative, and the DRM colour pipeline API being added
  upstream could be a home for it later.

## Using it

### Prebuilt image

The release has a LibreELEC 13 image (`.img.gz`) for the Raspberry Pi 4,
Pi 400 and CM4, built from LibreELEC master with these patches. The same
file works both ways:

- **Fresh install:** write it to an SD card with Raspberry Pi Imager,
  LibreELEC USB-SD Creator or balenaEtcher. It does not need to be unpacked
  first.
- **Update** of an existing LibreELEC 12 or 13 install: while LibreELEC is
  running, copy it to `/storage/.update`, through the `Update` Samba share
  (`\\LIBREELEC\Update`) or over SSH, and reboot. The update runs during
  that boot. The directory is on the ext4 STORAGE partition, so a PC with
  the card in a reader cannot reach it. Coming from 12 also moves Kodi 21
  to 22, which converts its databases and settings one way, so going back
  to 12 needs a backup made before the update.

Then:

1. Add `vc4.hvs5_pq=1` to `/flash/cmdline.txt`, on the same single line as
   the rest, and reboot. The file is on the FAT boot partition, so it can
   also be edited on a PC with the card in a reader. On the running system,
   run `mount -o remount,rw /flash` first. A LibreELEC update keeps this
   file.
2. On a TV with HDR, turn off Settings → Player → Videos → "Adjust display
   HDR mode" (advanced settings level). Otherwise Kodi sends HDR to the TV
   and the curve stays off.
3. During playback: Video settings → Tone mapping → BT.2390. Any method
   other than Off, including the default, turns the curve on.

Check: `cat /sys/module/vc4/parameters/hvs5_pq_crtc` is not 0, and `dmesg`
shows "HVS5 gamma: PQ to SDR curve loaded on channel 2".

These are unofficial builds. They are not supported by the LibreELEC team.

### Building

The patches were made for LibreELEC.tv master `a0fa50bc6e` (6 November
2026): Linux 6.18.60 (raspberrypi/linux `0b41724521c9`) and Kodi
`c0718c9a69c4` (Piers). The `libreelec/` directory mirrors the LibreELEC.tv
tree:

```sh
git clone https://github.com/LibreELEC/LibreELEC.tv
cd LibreELEC.tv
git checkout a0fa50bc6e
cp -r ../rpi4-hdr-tonemapping/libreelec/* .
PROJECT=RPi DEVICE=RPi4 ARCH=aarch64 make image
```

The Kodi patches are named `kodi-998.xx` and `kodi-999.xx` so that they sort
after LibreELEC's own Raspberry Pi patches in the same directory, which
they depend on.

## Repository layout

- `libreelec/packages/linux/patches/raspberrypi/`: the kernel patches for
  raspberrypi/linux rpi-6.18.y, one commit each:
  1. load the curve into channel 2 (`hvs5_pq`, `hvs5_pq_pwl`,
     `hvs5_pq_crtc`);
  2. apply it on HDMI0 (`hvs5_pq_gamma`);
  3. the BT.2020 to BT.709 plane matrix (`hvs5_pq_gamut`, `hvs5_pq_csc`).
- `libreelec/projects/RPi/patches/kodi/`: the Kodi patches, one commit
  each, in the order listed under [Changes](#changes).
- `tools/pwl_gen.py`: the curve generator. Other source peaks and white
  levels can be passed as arguments. It prints the value for
  `vc4.hvs5_pq_pwl=` on the kernel command line.
- `tools/colour_check.py`: the ΔE and Hable figures in this README, from
  frames extracted with FFmpeg.
- `tools/perf/`: the playback measurement scripts.
